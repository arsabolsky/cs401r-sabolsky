## Task 1: churn model and feature value

The Feature Store contains 9,999 customers and 13 engineered fields; the final model uses 11 numeric behavior features, leaving out the target, customer identifier, policy tier, and hand-built churn score. Gradient-boosted trees fit this dataset because they can learn threshold effects and interactions among recency, purchase frequency, basket size, and spend without requiring a large sample or feature scaling. Logistic regression would be a useful compact benchmark, but its linear decision boundary would need explicit transformations and interactions to capture those patterns. A neural net would add tuning and explanation costs on only about 7,000 training rows. The retention team needs a ranked outreach list and reasons they can discuss, so the tree model's gain ranking is a useful diagnostic, though customer-level reason codes would need SHAP or an equivalent reviewable explanation. I would switch to calibrated logistic regression if time-based validation showed no material tree-model lift and coefficients improved operational trust; a sequence model would be worth revisiting only with substantially more timestamped customer histories.

On the 3,000-customer held-out split, XGBoost 3.4.1 reached AUC 0.7821 versus 0.7232 for the recency-only baseline: +0.0589 AUC, with a paired-bootstrap 95% interval of [0.0404, 0.0776]. Precision@top-10% was 0.7167 and recall@top-10% was 0.3258. `days_since_last_purchase` had the largest gain (83.63), followed by `avg_basket_size_6m` (67.09) and `purchase_frequency_30d` (43.95). `total_spend_90d`, lifetime value, and average order value also contributed; online/store ratio, 90-day purchase frequency, and tenure had the lowest gains in this fit. Low gain is not proof a feature is useless: correlated predictors can divide split credit, and gain is not a causal effect.

I separately ablated `churn_risk_score`, the Lab 2 rule built from days since purchase and 30-day frequency. On the same Athena-backed rows, stratified split, seed, and XGBoost settings, the 11-feature model scored AUC 0.7821, precision 0.7167, and recall 0.3258. Adding the heuristic score changed those to 0.7806, 0.7133, and 0.3242. The paired AUC change was -0.0014 with 95% CI [-0.0065, 0.0041], which includes zero. Although the score received high split gain, it did not add measurable held-out performance, so I left it out of the registered model. The full aggregate comparison and gain values are in [`churn-risk-score-ablation.json`](lab3-evidence/churn-risk-score-ablation.json); the final feature plot is [`feature-importance.png`](lab3-evidence/feature-importance.png).

## Task 2: retrieval-augmented generation

The offer system uses RAG rather than fine-tuning. Its four Markdown sources describe loyalty, shipping, returns, and customer FAQ policies; no product catalog is available. Retrieval supplies auditable policy text at request time, so policy edits can be applied by updating the corpus and rebuilding the local index. Fine-tuning would make small eligibility corrections harder to trace and would not reliably keep changing rules current.

`rag_offer_system.py` splits Markdown at headings, then creates overlapping 1,200-character windows with 180 characters of overlap. Each chunk retains its document ID, section, and stable chunk ID. Titan Text Embeddings V2 produces normalized 1,024-dimensional vectors in a local FAISS inner-product index, built once per process. Strategy C combines tier and channel query terms with a loyalty/shipping metadata filter. I did not add a reranker: this four-document corpus is small, and the strategy comparison showed C retrieved all reference context for the four original cases before the fallback was added.

The prompt corrects the starter's Gold/Platinum thresholds and prohibits free expedited shipping, invented discounts, codes, deadlines, catalog claims, and unsupported eligibility. The Feature Store tier reflects lifetime value, while policy eligibility uses trailing-12-month spend; the system therefore phrases tier benefits conditionally. A deterministic claim filter replaces outputs containing several known unsupported claim types with a policy-backed fallback. It is a narrow guardrail, not a semantic verifier.

After Anthropic's first-time-use form and model agreement became available in the personal account, I ran the four unchanged cases with Haiku 4.5 for both generation and RAGAS judging. Strategy C scored 0.458 faithfulness, 0.325 answer relevancy, and 0.608 context recall; the fallback activated in three cases. This run is in [`rag_eval_20261025T021342.csv`](lab3-evidence/rag_eval_20261025T021342.csv). Both generation and judge changed from the Nova comparison, so the scores describe this configuration and do not isolate Haiku's generation effect. RAGAS scores are judge estimates, not direct measurements; the four-case sample and the heuristic fallback are the main production risks.

With ten times the time or data, I would represent policy benefits and eligibility as structured records and validate each generated claim against those records before release. I would add a human-reviewed holdout spanning more policy boundaries and measure both policy violations and offer usefulness, rather than optimizing one judge score.
