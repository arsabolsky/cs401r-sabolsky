Track B — RAG offer generation

## Task 1: churn model choice and observed results

The churn pipeline uses XGBoost gradient-boosted trees. The training set has roughly 7,000 rows and 11 numeric behavior features, so tree boosting captures threshold effects and interactions without the scaling and feature engineering a neural network would need. It also provides a gain-based feature-importance view that a retention analyst can discuss. The model excludes `churn_label` and `loyalty_tier` from its inputs to avoid leakage and the lifetime-value/policy-tier mismatch.

The graded Athena-backed validation set contained 3,000 customers. The saved metrics are ROC AUC 0.7821, precision in the top 10% 0.7167, and recall in the top 10% 0.3258. The recency-only baseline AUC was 0.7232, for a lift of 0.0589; the bootstrap 95% interval was [0.0404, 0.0776], excluding zero. `days_since_last_purchase` had the largest gain in the feature-importance plot, followed by `avg_basket_size_6m` and `purchase_frequency_30d`. These results support ranking customers for review; they do not mean a customer will churn with certainty. Platinum had too few observations for a reliable tier estimate, and Silver was the weakest sufficiently sized tier. With substantially more labeled data, I would compare calibrated gradient boosting and a time-aware sequence model, while preserving the recency baseline and time-based validation.

## Task 2: retrieval-augmented generation

The offer system uses retrieval-augmented generation (RAG) rather than fine-tuning. The corpus has four Markdown files: loyalty terms (`POL-LOY-011`), shipping (`POL-SHP-007`), returns (`POL-RET-004`), and customer FAQ (`KB-FAQ-022`). It contains policy, not a product catalog, so the customer profile supplies the categories and retrieved policy supplies permissible benefits. RAG lets policy updates take effect by replacing source text and rebuilding a local index; fine-tuning would bake policy into model weights and make small policy corrections harder to audit.

`rag_offer_system.py` splits documents by Markdown section and overlapping 1,200-character windows with 180 characters of overlap. Each chunk retains document ID, section, and a stable chunk ID. Amazon Titan Text Embeddings V2 creates normalized 1,024-dimensional vectors. A local FAISS inner-product index is built once per process and reused for queries. Retrieval returns four chunks. Strategy C combines tier and channel terms with a metadata restriction to loyalty and shipping policies. I did not add a cross-encoder reranker: the corpus is small, retrieval is local, and the evaluation showed strategy C retrieved all relevant context for the four supplied cases before guardrails. The experiment compares A, B, and C in the evidence summary.

The prompt corrects the starter's three planted policy errors: Gold ends at $4,999.99, Platinum begins at $5,000, and no tier gets free expedited shipping. It also prohibits invented discounts, codes, deadlines, thresholds, catalog claims, and unsupported individual eligibility. The feature-store `loyalty_tier` is based on lifetime value, but policy tiers are based on trailing-12-month spend. Since the profile does not contain that spend, tier-specific benefits are phrased conditionally. The generator's output is screened for common unsupported promotion, catalog, birthday, unused-credit, and unconditional-tier claims. When a check fires, a deterministic fallback selects a tier benefit only if it can verify the benefit in the loyalty policy corpus and adds the supporting chunk to the returned evidence.

The course starter targets Claude Haiku 4.5. In the personal AWS account, Bedrock returned an account-level error requiring Anthropic use-case details before inference. I did not submit that form. The recorded evaluation therefore used Amazon Nova Lite for the initial generation comparisons and Nova Pro as the judge; final guarded generation and judging used Nova Pro. The model IDs are retained on every CSV row. In matched Nova Pro-judge runs with Nova Lite generation, strategy C averaged 0.545 faithfulness, 0.311 answer relevancy, and 1.000 context recall over four cases. The controlled profile-context ablation changed context recall from 1.000 to 0.838 when profile text was omitted, while faithfulness and relevancy rose; this is one small four-case comparison. After adding the policy fallback, the final C run averaged 0.667, 0.136, and 0.850 respectively. The fallback activated for all four customers. It improved grounding relative to the prior C run but made the text less relevant to the judge's preferred offer phrasing. These targets are diagnostic, not gates.

The main risks are a four-case evaluation set, model-based judge variability, policy changes not reflected in the Markdown corpus, and heuristic output checks that cannot detect every semantic error. With ten times the time and data, I would represent benefits and eligibility as structured policy records and validate generated claims against those records before release. I would also expand the test set across policy boundaries, use a separate human-reviewed holdout, and measure both policy violations and usefulness rather than optimizing a single RAGAS score.
